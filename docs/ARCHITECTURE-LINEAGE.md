# Architecture Lineage: CS-OLabs → DL-VizLab

DL-VizLab carries the architecture of the CS-OLabs Multi-Aspect Visualization Framework (Swaminathan et al., *SN Computer Science* 6:284, 2025) from procedural programs to neural-network training. This document maps each component and states what had to change because the domain is tensor and gradient semantics, not procedural instruction semantics. CS-OLabs component names and the two quotations below are as given in the project brief, which summarises the base paper. The paper itself could not be opened from the build environment, so quotations should be checked against it before the manuscript cites them.

| CS-OLabs component | DL-VizLab counterpart | What changed, and why |
|---|---|---|
| **Program model**: the program to be visualised, with its execution points | **Neural Program Model (NPM)** (`src/core/npm/`, `docs/NPM-SPEC.md`) | A training run is not written by the learner; it is generated. The NPM is therefore emitted by the engine as it trains (`emitter.ts`), not parsed from source code. Its instructions operate on tensors, not scalars and variables. Each one carries a structured nesting path (epoch / batch / example / phase / layer) and operand references to earlier results, so data flow is explicit across the forward pass, the backward pass and the update. Instruction kinds are typed and registered (`kinds.ts`), with a generated JSON Schema, a grammar and lossless serialisation. |
| **Virtual Execution Engine**: executes the program step by step and exposes its state | **Execution engine and trace navigator** (`src/core/engine/`, `src/core/npm/navigator.ts`, `state.ts`, `store.ts`) | Execution of a gradient-based program has a backward phase that depends on stored forward values. The engine records the whole run once (float64, deterministic from a seed). The navigator then moves a cursor over the recorded trace rather than re-executing. State at any cursor is *reconstructed*: parameters, every layer's activations and gradients, optimiser state. That makes stepping **backwards** exact. Long runs are bounded by batch checkpoints and recomputation (NPM-SPEC §9), a concern a procedural program of classroom size does not have. |
| **Visual Action Translator**: maps each executed step to visual actions | **Visual mapping registry** (`src/views/registry.ts`) and **explainer registry** (`src/explain/registry.ts`) | Each instruction kind maps to a flow direction (forward / backward / update / none) and a target (units, edges, bias, loss, layer). The views use that mapping to highlight, animate and set the mode indicator. Because the meaning of a tensor step is mathematical, a second registry translates each instruction into its general formula, the same formula with the step's numbers, and a sentence. |
| **Three visualizations** | **Three synchronised views**: A execution (`src/views/execution/`), B training state (`src/views/training/`), C structure (`src/views/structure/`) | The three aspects become the network executing one instruction (or, for CNNs, the convolution view), the training run over time (loss, accuracy, gradient magnitude per layer, decision boundary), and the architecture with its shapes and parameters. All three render only from the reconstructed state at one cursor. |

## Two generalisations of the predecessor architecture

**Automatic granularity.** In CS-OLabs, pause points are "identified and prespecified in the model code manually by the subject matter experts", so execution granularity is hand-authored for each experiment. In the NPM, granularity units are derived automatically from each instruction's nesting path (NPM-SPEC §5.2, `unitKey` in `src/core/npm/stats.ts`, used by `navigator.ts`). Operation, layer, phase, example, batch and epoch boundaries follow from the path alone. No experiment author marks any pause point, and a new instruction kind or experiment gets all six granularities without further work.

**Extensibility.** The base paper's comparison table (its Table 5) rates CS-OLabs **L (Limited)** on ease of extension. The NPM targets that acknowledged limitation with four registration points (NPM-SPEC §7.1):
- a differentiable op (`registerOp`);
- an instruction kind and its op mapping (`registerInstructionKind`, `registerOpMapping`);
- an explainer (`registerExplainer`);
- a visual mapping (`registerVisualMapping`).

The JSON Schema is generated from the registered kinds. The LayerNorm tutorial (NPM-SPEC §7.2, `examples/layernorm.ts`) adds a new layer through these points without editing any existing file. `tests/unit/extension.test.ts` verifies that it passes a finite-difference gradient check and trains inside a model into a schema-valid, fully explained trace. The extension still requires writing TypeScript; it is easier, not effortless.
